# W09 Disaster Recovery Runbook — DRAFT / not owner-approved

## Scope and evidence boundary
Production recovery is not proven by this document. W01 PR #439 accepted a historical schema-only snapshot and two staging policy deltas; exact migration history equality was excluded. The current live schema must be captured independently. W09 never restores into production during a drill. No live customer rows, object bytes, credentials or provider tokens in CI, Git, public logs or disposable staging.

## Responsibility and incident decision
Proposed roles (owner must nominate actual people and backup contact): Human CEO/owner = incident commander, approves target, recovery point, data-loss tradeoff and cutover; backend operator = database/Storage backup and restore; release operator = Vercel/deployment/DNS; security reviewer = access, credential rotation, tenant validation and incident evidence. One person may hold multiple roles but a separate reviewer is required for cutover. Escalate to owner immediately for missing backup, checksum failure, unauthorized access or inability to meet recovery target. Provider support tickets are owner-authorized.

## Inventory and targets (not measured SLA)
- Supabase Free: do not rely on provider daily backups/PITR. Use encrypted independent logical backups; verify dashboard entitlement and latest usable artifact each drill.
- DB: daily target RPO <=24h; RTO <=4h for small dataset (provisional, end-to-end must be measured). Storage: same daily recovery point, include all private/public buckets, object version/size/content-type/metadata/hash and application references. RTO <=4h provisional. No assertion that targets are achieved today.
- Vercel: retain last known-good production deployment and source SHA; rollback target <=30min including smoke/security checks, not measured. Application rollback does not restore DB, Storage, provider credentials or revoke previously issued tokens. Old deploy may predate security fixes.
- Proposed retention: 7 daily + 4 weekly + 3 monthly encrypted copies, subject to owner approval, capacity, data minimization and legal deletion policy. At least one off-project copy with independent access. Backups must be encrypted in transit/at rest, key in separate owner-controlled vault, least-privilege access and restore audit. Never store backup data or secrets in public repository. No paid storage or plan upgrade without approval.
- Integrations: inventory names/config only (Vercel environment scopes, Supabase Auth/OAuth redirect URLs, Edge Functions, secrets, cron/webhooks, DNS/Cloudflare, Google Workspace, Microsoft 365, GitHub App, Stripe, Resend, LinkedIn, Bing, Browserbase, OpenAI and other enabled providers). Store credentials only in independent encrypted secret manager with recovery access. Verify ownership, redirect allowlists, token revocation/rotation, webhook signing and provider settings before enabling. Dry run must use mock/sandbox credentials or disabled integrations.

## Backup procedure (operator-controlled environment)
1. Record UTC backup start, source project identity, Git SHA, live deployment, Postgres version, migration ledger fingerprint, schema/catalog fingerprint, bucket list and integration/flag inventory. Read dashboard Database > Backups; record plan and available restore points. No credential values in log.
2. Use pinned Supabase CLI and PostgreSQL compatible version. Check help before executing. In a trusted operator machine use encrypted storage and secret-managed direct/pooler database URL. Follow official Supabase backup/restore instructions: export custom roles, schema and data separately with `supabase db dump --db-url "$DB_URL" --role-only -f roles.sql`, `supabase db dump --db-url "$DB_URL" -f schema.sql`, and `supabase db dump --db-url "$DB_URL" --data-only --use-copy -f data.sql`. This is a procedure requiring controlled access, NOT a command already executed. Do not put actual URL on a shared terminal or shell history; use environment only in private shell, disable tracing, restrict access. Inspect managed schemas excluded by default; preserve auth users/identities and application-dependent managed schema data, custom triggers/policies and migration ledger separately following supported provider restore procedure. Never assume default dump includes all needed data. Do not export service secrets into SQL.
3. Independently enumerate all bucket objects using a server-only authorized Storage/S3 client, paginate, download bytes, store relative keys and metadata + SHA-256, encrypt all artifacts. Do not use signed public links or log file names. DB storage metadata is not file bytes. Preserve bucket privacy and custom policies; restore object bytes through Storage API rather than writing storage.objects directly.
4. For consistent DB/object checkpoint, use approved write quiescence or snapshot/versioning with reconcile/retry; record start/end, versions and gaps. If records change during independent capture, reject as inconsistent. A write freeze on production requires owner approval.
5. Verify archive checksums, counts, cross-reference integrity, encryption/decryption using authorized account and second copy. Track last successful recoverable checkpoint and backup freshness; alert owner if older than 24h. Never treat existence of a dump as recoverability. Schedule daily job on an authorized trusted host; no scheduler or destination is yet assumed configured.

## Isolated restore and drill
- Operator provisions new disposable local/staging environment (never production; exact ref/hostname allowlist, no production secrets or real customer data in routine synthetic drill). Record incident declaration UTC; start RTO clock before provisioning. Disable outbound jobs, email, OAuth callbacks to real providers, Stripe live, AI and external writes; assert flags and no production network bindings. Use a synthetic backup of actual current application schema/fixtures. For real production recovery validation with customer data, require separate owner/data-protection approval and restricted recovery environment.
- Validate source archive hashes. Restore roles/schema/data to clean target in provider-supported order with stop-on-error. Restore auth identities, extensions and custom policies/triggers; verify catalog and migration ledger against source, distinguish W01 historic snapshot from current main. Preserve secrets via vault recovery, not dump. Recreate buckets with original privacy and file metadata; re-upload verified bytes through Storage API. Restore refs and verify no dangling objects.
- Validate counts, deterministic fixture primary keys, checksums, FKs, tenant A/B/C access and denial, RLS policies and SECURITY DEFINER grants, auth login/session/revocation, private authorized downloads byte-for-byte, anonymous/cross-tenant and revoked access denial, audit continuity and disabled external actions. Execute app smoke tests against restored database and review actual build/flags. Compare latest recovered transaction with simulated incident cutoff and count deliberately absent post-checkpoint rows/files; record measured RPO and RTO. Fail closed on any mismatch.
- Local component drill: `node scripts/qa/w09-local-restore-drill.mjs` on clean Linux Docker host with pinned Supabase CLI 2.84.2. Creates two distinct local stacks, pg_dump/pg_restore of full synthetic fixture schema, real private Storage API upload/download, hashes, RLS and simulated post-backup loss. Does NOT cover full current RYTHM app schema, auth identity restore, application route tenant checks or cloud restore. Public CI summary contains synthetic metrics only; for restricted log run on trusted host with `W09_KEEP_PRIVATE_LOG=1`, keep resulting 0600 JSON outside Git, encrypted. Never run against cloud. Clean up local stacks and payloads; keep redacted evidence separately.
- Full W09 gate: current app schema and migration ledger + representative app fixtures with Auth/Storage and live staging application security verification; actual recovery time/data loss; restricted drill log; approved runbook and named owners. Component test alone does not satisfy gate.

## Vercel recovery / rollback review
1. Inspect current production domain deployment and last eligible READY deployment. Record SHA, deployment ID, alias and compatible schema/migration/flag state. Verify candidate contains security fixes; if reverting would remove them, prefer forward fix or restrict traffic with owner approval. Never roll back DB just because app rolls back.
2. On owner-approved incident only: Vercel project > Production Deployment > Instant Rollback > select reviewed candidate > confirm aliases and previous build configuration. CLI alternative: `vercel rollback <deployment-id>`, then `vercel rollback status`. Hobby permits previous eligible production deployment only. Rollback reuses historical environment and cron state; recheck flags and provider configuration. No actual production rollback in drill.
3. Validate health, login, tenant authorization, private files, audit, disabled external actions and 5xx rate. If failed, maintain isolation, escalate; promote reviewed known-good deployment only with owner approval. `vercel promote <deployment-id>` re-enables production auto-assignment. No destructive schema downgrade.
