## Personal AI memory disposition

The candidate migration `20261123151000_w17_personal_memory_erasure.sql` adds an operator-only command for one reviewed personal AI memory. After documenting identity verification and selecting a record within the account-scoped case, the database operator calls `privacy_dispose_personal_memory` with the case ID, memory ID and `erase` or `retain`. Retention requires a reviewed legal-obligation or legal-claims basis and a future review date. The operator records the supporting reference in the restricted case history. Record content stays out of this audit table.

A retention decision blocks ordinary updates and deletions, including cascading account deletion. On review, an operator releasing a hold must lock the affected memory and update the ledger row with `released_at`, `released_by` and the separately verified `release_request_id` in one transaction. Record the authorization and rationale in the restricted case history. The scheduled review date is a reminder for the operator. It does not release a hold automatically. Retained content still needs separate operational restriction of access and use when required.

An erase operation deletes the record and records its disposition in one transaction. A retry with the same in-progress verified case returns the existing outcome. The command does not close the request. Continue reviewing other surfaces, including project and organization data, derived files, processor records, logs, and backups. Avoid dropping the evidence ledger during any rollback after it contains dispositions.

Account erasure defaults to deleting eligible personal data. For an in-progress, verified erasure case, the operator can call `privacy_erase_account_memories(request_id)` repeatedly to erase owned memories from the subject's personal workspace. The batch records each disposition and reports remaining eligible records and unreleased holds. A record whose authorship or retention disposition needs review must be resolved separately. Stop writes by the subject and reconcile pending work before treating the account as erased. This command covers personal memories. The complete Auth, Storage, shared-record, provider and backup workflow still requires separate completion evidence.

## Reviewed account export

A database operator can run `privacy_collect_personal_export(request_id)` for an in-progress, verified access, export or portability case scoped to an account. The result includes allowlisted Auth and profile fields, preferences, personal projects, conversations and messages, personal memories, saved prompts, file metadata and extracted chunks. The workspace is resolved from the verified subject. Organization data, credentials, storage paths and internal case notes are excluded. Review the draft for other people's information and for the applicable request type before secure delivery. Reconcile file binaries, organization/controller data, processor records and any other uncovered source separately. Keep the draft out of tickets, logs and the case evidence ledger.

For a verified account deletion case, run `privacy_inventory_account_dependencies(request_id)` before deciding how to handle related records. It returns counts of direct foreign-key references in the application and Storage schemas, including cascading links. Inspect ownership transfers, shared records, holds and immutable ledgers before account deletion. Check indirect references, Storage binaries, processors and backups independently.

## Personal file erasure

The signed-in file deletion route verifies ownership and waits for ingestion to reach a terminal state. It removes the binary through Storage, then clears the stored extraction and deletes the file metadata and chunks in one database transaction. An interrupted Storage-to-database operation can be retried. Metering and ledger records are preserved for the separate retention decision. The file is matched to an extraction by its workspace, user and original ingestion key, including failed ingestions that never linked the usage row on the file.

Account erasure still requires verified identity and authority, reconciliation of queued work and all eligible data, and review of dependencies that prevent Auth deletion. Review organization ownership and references, retained usage records, provider copies, and backup copies before closing a case. A successful synthetic identity deletion verifies Auth and token behavior for that scoped fixture, including stale access and refresh tokens. It does not resolve the deletion policy for customer accounts with shared or retained history.
