# WF-001 — Unified Workflow Architecture

Status: **Architecture baseline for Batch 2.1**  
Scope: RYTHM Company OS MVP v1.0  
Authority: Human CEO / Product Owner  
Owner of orchestration: B-001 Executive Orchestrator

## 1. Purpose

WF-001 defines the canonical architecture for how governed company work moves through RYTHM. It connects projects, ideas, meetings, legal reviews, decisions, approvals, actions, memory, progress, and audit into one operating loop.

Canonical MVP operating loop:

`Project → Idea/Issue → Meeting → Synthesis → Legal Review when relevant → Human CEO Decision → Approval when required → Action → Progress → Memory/Audit`

This architecture is the source of truth for Batch 2.1 and for all later workflow-dependent features such as Project Pulse, Attention Center, notifications, analytics, automation hooks, and investor/demo workflows.

## 2. Architecture principles

1. **Project is the primary operating context.** Governed work should resolve to a project whenever a project context exists.
2. **Human CEO retains consequential authority.** Agents may analyze, recommend, coordinate, triage, and escalate but may not bypass the Human CEO decision or approval gates.
3. **Every consequential transition is auditable.** Important creation, state change, recommendation, approval, rejection, escalation, and completion events must be recorded.
4. **Relationships are explicit.** Cross-entity linkage must use persisted identifiers, not inferred UI-only associations.
5. **Workflow state is derived from governed facts.** UI labels must not invent workflow state independent of persisted business records.
6. **External action is opt-in and separately governed.** MVP workflow completion does not imply permission to act outside RYTHM.
7. **Failure must be resumable.** Transient AI/runtime failures must not corrupt authoritative records or silently advance workflow state.
8. **Cost and risk are first-class metadata.** Agent execution must remain bounded by configured budget and risk policies.
9. **One source of truth per business fact.** Duplicate representations may exist for read models, but the canonical object and canonical event must remain identifiable.
10. **Future automation subscribes to events; it does not bypass governance.** Event-driven extensions may recommend or queue work but cannot skip decision, approval, legal, or external-action controls.

## 3. Canonical entities

### 3.1 Project

The project is the bounded operating context for a business objective.

Canonical responsibilities:
- objective and current stage;
- progress and current governed step;
- relationship root for ideas, meetings, decisions, actions, memory, approvals, legal reviews, and timeline events;
- blocker and next-step visibility.

### 3.2 Idea / Issue

An idea or issue is an uncommitted input requiring triage, research, discussion, deferral, or decision.

Rules:
- idea capture does not modify project scope automatically;
- an idea may be routed to one or more relevant agents;
- an idea may be surfaced in a scheduled or topic-specific meeting;
- disposition must be explicit: inbox, research-required, scheduled-for-review, deferred, accepted-for-decision, rejected, or archived.

### 3.3 Meeting

A meeting is a governed deliberation container.

Responsibilities:
- decision question and agenda;
- authorized participants;
- Human CEO optional participation;
- persistent deliberation turns;
- B-001 synthesis;
- meeting summary and language controls;
- legal relevance triage;
- link to the resulting decision.

### 3.4 Legal Review

A legal review is an advisory issue-spotting record generated by A-106 when requested or recommended.

Rules:
- it does not constitute formal legal advice or legal approval;
- it distinguishes strategic conditions from execution-level legal review;
- licensed-counsel requirements block the affected execution path, not unrelated strategic direction;
- the Human CEO may request review even when B-001 does not flag legal relevance.

### 3.5 Decision

A decision is a Human CEO-authorized resolution of a governed question.

Responsibilities:
- selected option;
- rationale;
- risk level;
- linkage to meeting or direct decision context;
- legal/approval constraints;
- creation of downstream actions where applicable.

Agents cannot create a final consequential decision on behalf of the Human CEO.

### 3.6 Approval Request

An approval request is a separate governance gate for decisions/actions whose risk requires additional explicit authorization.

MVP rule:
- low/medium-risk decisions may be finalized directly by the Human CEO where policy permits;
- high/critical decisions route through the Approval Engine;
- approval state must be auditable.

### 3.7 Action

An action is executable governed work produced by an approved decision, project plan, or operational need.

Responsibilities:
- owner;
- status;
- priority/deadline where applicable;
- source decision/project;
- completion evidence;
- audit history.

### 3.8 Memory

Company Memory stores approved organizational context that should persist beyond an individual conversation or meeting.

Rules:
- draft content is not authoritative;
- approved memory may be used as company context;
- memory may link to projects, decisions, meetings, or source evidence;
- archival must not destroy audit history.

### 3.9 Progress Event / Project Pulse

Progress events record material changes to project progress, stage, milestones, blockers, and governed next steps.

Project Pulse is a read/attention experience built from authoritative progress records and events.

### 3.10 Audit Event

Audit events provide the immutable-enough history of consequential system behavior.

At minimum they identify:
- actor type;
- actor identity where available;
- event type;
- object type/id;
- organization;
- risk level where relevant;
- payload sufficient to explain the transition without exposing secrets.

## 4. Canonical relationship graph

Minimum required relationships for MVP:

- Project → Ideas: one-to-many
- Project → Meetings: one-to-many
- Project → Decisions: one-to-many
- Project → Actions: one-to-many
- Project → Memory: one-to-many or many-to-many through explicit references
- Project → Approvals: one-to-many
- Project → Progress Events: one-to-many
- Meeting → Agent Session: one-to-one or one-to-many by version/retry policy
- Meeting → Legal Reviews: one-to-many, retaining audit history
- Meeting → Decision: zero-or-one final governed decision per decision question unless explicitly versioned
- Decision → Actions: one-to-many
- Decision → Approval Request: zero-or-one active approval path per governed decision version
- Decision → Memory: zero-to-many approved memory records

No UI-only relationship is considered authoritative.

## 5. Ownership and authority rules

### Human CEO
- owns consequential decision authority;
- approves scope exceptions;
- may request legal review manually;
- approves or rejects high/critical approval requests as policy requires;
- may pause or terminate agent execution.

### B-001 Executive Orchestrator
- coordinates governed work;
- prepares meeting context;
- routes relevant ideas/issues;
- synthesizes deliberation;
- performs legal relevance triage;
- escalates uncertainty, blockers, risk, or missing authority;
- may not make final consequential decisions.

### Specialist agents
- produce advisory analysis within their mandate;
- may challenge other agent positions;
- may recommend action;
- may not mutate consequential state unless an explicit governed capability authorizes that mutation.

### A-106 Legal & Regulatory Counsel
- performs advisory legal issue-spotting;
- classifies legal applicability;
- recommends conditions or licensed-counsel review;
- does not provide formal legal approval.

## 6. Lifecycle boundaries

### Project lifecycle

`draft → active → blocked/on_hold (optional) → completed → archived`

Project business stage is separate from record lifecycle. Stage may represent discovery, decision, execution, validation, etc.; record status represents whether the project itself is operational.

### Idea lifecycle

`inbox → triaged → research_required / scheduled_for_review / deferred → accepted_for_decision / rejected → archived`

### Meeting lifecycle

`draft → scheduled (optional) → running → completed → archived/cancelled`

### Decision lifecycle

`proposed → pending_human_decision → pending_approval (when required) → approved/rejected → superseded (optional)`

### Action lifecycle

`planned → ready → in_progress → blocked → completed / cancelled`

### Legal review lifecycle

`requested → running → completed / failed`

### Memory lifecycle

`draft → approved → archived`

The detailed cross-entity workflow state machine is specified in WF-005; WF-001 defines the lifecycle boundaries that later implementation must respect.

## 7. Integration rules

1. A meeting linked to a project must persist the project relationship before deliberation begins.
2. A decision created from a meeting must preserve meeting and project provenance.
3. Actions created from a decision must preserve decision and project provenance.
4. Legal review must preserve meeting/session provenance and the Human CEO requester when manually requested.
5. Approval requests must preserve their triggering decision/action and risk reason.
6. Memory created from a decision or meeting must retain source references.
7. Project progress changes must be attributable to an approved action, explicit CEO change, governed milestone, or system rule.
8. UI navigation must use persisted relationships rather than query-string-only associations.

## 8. Event and audit rules

The event model is specified in WF-002. WF-001 establishes these mandatory rules:

- every consequential state transition emits or records one canonical domain event;
- every canonical domain event has an auditable record or a traceable source record;
- event names are stable and semantic, not UI-specific;
- retries must not duplicate completed business transitions;
- failed runtime attempts may be retained for audit but must not count as completed workflow turns;
- downstream consumers must be idempotent where replay is possible.

## 9. Failure and recovery rules

- AI/network timeout: preserve current state; allow safe retry/resume.
- empty/invalid agent output: do not record as a valid deliberation turn.
- legal-review formatting failure: normalize safely or fail without advancing legal state.
- approval failure: decision remains pending; execution cannot advance.
- database write failure: no optimistic workflow advancement may be shown as final.
- duplicate request: return existing authoritative result when the transition is already complete.
- recovery migrations must preserve Human CEO decisions and audit history.

## 10. Security and organization boundaries

- all persisted workflow records are organization-scoped;
- RLS remains the primary database isolation boundary;
- server-only secrets remain outside client bundles;
- service-role usage must be narrowly scoped and never used to bypass governance rules;
- agent execution and external actions are controlled independently;
- external actions remain disabled for MVP unless a separate approved capability explicitly enables them.

## 11. Cost and observability requirements

Agent-backed workflow steps must expose or record:
- model identifier;
- input/output token usage where available;
- estimated provider cost;
- meeting/session budget cap;
- failure reason;
- retry/recovery status.

CEO-facing commercial display currency is EUR. Provider-native currency may remain internally for reconciliation.

## 12. UI/navigation contract

Every core object view should be able to surface its governed context without forcing the CEO to reconstruct relationships manually.

Minimum contextual navigation targets:
- Project → ideas, meetings, decisions, actions, memory, approvals, timeline
- Meeting → project, decision, legal review, related idea(s), resulting actions
- Decision → project, source meeting, approval, actions, memory
- Action → project, source decision, evidence/history
- Idea → project, assigned/relevant agents, related meeting/decision

Detailed UI implementation belongs to Batch 2.1.7 and Batch 4; this document defines the required information architecture contract.

## 13. Development rules for workflow-connected features

A workflow-connected feature is not complete unless it answers all of these:

1. What is the canonical entity?
2. What project/organization does it belong to?
3. What creates it?
4. What state transitions are valid?
5. Who has authority for each transition?
6. What event represents each consequential transition?
7. What audit evidence is retained?
8. What downstream objects may be created?
9. What happens on retry/failure?
10. What existing relationships must be navigable?

Features that cannot answer these questions must not introduce a new business-state mutation.

## 14. Batch 2.1 dependencies

WF-001 is the parent architecture for:
- WF-002 Company Event Model;
- WF-003 Entity Relationship Engine;
- WF-004 Operating Timeline;
- WF-005 Workflow State Machine;
- database/backend integration;
- UI integration/navigation;
- production end-to-end validation.

Any later implementation that conflicts with WF-001 requires an explicit architecture change recorded in the repository and, if it changes frozen MVP scope, Human CEO approval through the scope-change process.
